# Exercise 13: HardFault Debugging Demo

## Objective

To deliberately trigger a HardFault exception on the STM32F407VG microcontroller and investigate the exception using GDB and Cortex-M4 system registers.

## Hardware

- STM32F407G Discovery Board
- STM32F407VG Microcontroller
- ARM Cortex-M4 Processor

## Software and Tools

- ARM GNU Toolchain
- VS Code
- WSL Ubuntu
- OpenOCD
- GDB

## Concepts Covered

- HardFault exception
- Cortex-M4 exception handling
- Invalid memory access
- IPSR (Interrupt Program Status Register)
- Exception numbering
- GDB debugging

## 1. HardFault Exception

A HardFault is an exception generated by the Cortex-M4 when a serious fault occurs or another fault cannot be handled by its corresponding handler.

In this exercise, a deliberate invalid memory access is used to generate a fault.

## 2. Generating a HardFault

An invalid memory address is assigned to a pointer:

```c
volatile uint32_t *fault_address = (volatile uint32_t *)0xFFFFFFFFU;
```

The following statement attempts to read from that address:

```c
fault_value = *fault_address;
```

This access is expected to generate a memory-related fault, which can escalate to HardFault if the corresponding configurable fault handler is not enabled.

## 3. HardFault Handler

A custom `HardFault_Handler()` is implemented to take control when the processor enters the HardFault exception.

The initial handler uses an infinite loop to keep the processor inside the exception handler for debugging.

## 4. IPSR Register Inspection

The IPSR (Interrupt Program Status Register) identifies the currently active exception.

The exception number is stored in the lower 9 bits of the xPSR register.

Important values:

| IPSR Value | Exception |
|---|---|
| 0 | Thread mode |
| 2 | NMI |
| 3 | HardFault |

The IPSR value can be captured in C using inline assembly:

```c
__asm volatile(
    "MRS %0, IPSR"
    : "=r" (active_exception)
);
```

## 5. GDB Debugging

GDB is used to inspect the processor registers after the HardFault occurs.

Useful commands:

```gdb
info registers
p/x $xpsr
p/x ($xpsr & 0x1FF)
p active_exception
```

The expected exception number for HardFault is:

```text
active_exception = 3
```

## 6. Build and Debug

The firmware is compiled using the ARM GCC toolchain and flashed using OpenOCD.

GDB is used to connect to the target, load the firmware, continue execution, and inspect the processor state when the fault occurs.

## Conclusion

This exercise demonstrates how to deliberately generate a HardFault exception and investigate the processor's exception state using IPSR and GDB. It provides practical experience with Cortex-M4 exception handling and low-level embedded debugging.
